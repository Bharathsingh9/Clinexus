1. Mission and scope
Implement the five-agent pipeline of the paper "An Adaptive Multi-Agent LLM-Based Clinical Decision Support System Integrating Biomedical RAG and Web Intelligence" (the base paper), plus four approved extensions: A Claim Verification Agent, B Explicit Abstention, C Evidence-Level Provenance, D Human-in-the-Loop Review. The result is a research tool that supports a clinician. It is not a medical device and never finalizes a decision.
Paper fidelity: tag every statement about the paper in docs as [PAPER-VERIFIED: section], [PAPER-GAP], or [ENGINEERING-DECISION: id]. If the paper PDF is not in the repository, tag everything about it [PAPER-UNVERIFIED] and treat the agent list in this spec as authoritative.
Out of scope (do not build): diagnosis finalization, prescriptions or dosing, treatment orders, EHR/FHIR integration, image or audio input, multilingual support, model fine-tuning, a dynamic agent router, an agent-dependency graph view, self-registration or SSO, email or notifications, and any dataset not listed in Section 9. A MedQA adapter is built only if MedQA files are found in datasets/medqa/ during the Phase 0 audit; otherwise it is BLOCKED and not built.

3. Workflow (LangGraph)
Nodes, exactly these, in this order: validate_case -> clinical_text_clarifier -> clarification_check -> symptom_rag_analyzer -> evidence_based_scanner -> clinical_data_fusion -> claim_verification -> evidence_safety_gate -> one of (adaptive_optimizer | finalize_ready | finalize_abstain) -> persist_and_finish.
The optimizer routes back to the earlier node it selects (symptom_rag_analyzer, evidence_based_scanner, clinical_data_fusion, or clarification_check); every revision passes through claim_verification and evidence_safety_gate again. The five original agents are the Clarifier, RAG Analyzer, Scanner, Fusion, and Optimizer. Claim verification and the safety gate are extensions A and B.
Routing is deterministic code, never an LLM. clarification_check: any blocking clarification question sets state EVIDENCE_REVIEW_REQUIRED and halts for clinician input; non_blocking questions continue and appear in the report.
evidence_safety_gate takes the first matching rule:

Out-of-scope request (treatment, prescription, dosing, non-biomedical)

A high confidence never overrides rules 1 to 4; confidence can only add an abstention reason. The optimizer cannot change rules, thresholds, or claim statuses. The iteration counter increments once per optimizer call; at the maximum the optimizer is not called again and the gate must finalize. Reaching the budget is never success. The gate is one pure function evaluate_gate(state, settings) -> GateDecision with an exhaustive truth-table test.
Material claim = any claim whose category is not background. Safety-critical claim = category in {diagnostic_consideration, red_flag, contraindication, urgency, drug_interaction}.
Failure semantics: each node writes an AgentExecutionRecord (SUCCEEDED | DEGRADED | FAILED, start and end time, input hash, output hash, error code). A DEGRADED or FAILED node is visible downstream in state.warnings or state.errors. A failed required node (Clarifier, Fusion, Verifier) ends the run FAILED. A failed Scanner is DEGRADED (local evidence only) and lowers source_availability. Never treat an exception, timeout, or empty result as success.
4. The five original agents
Each agent: one module, one class with one public run(input) -> output, Pydantic input and output validated at the boundary, one unit-test file, dependencies injected by constructor. An agent never imports another agent.
4.1 Clinical Text Clarifier (AGT-1). In: CaseSubmission. Out: ClinicalCase. Extract only what is stated: symptoms with onset, duration, severity, progression, associated symptoms; age, sex, history, medications, allergies, vitals. Keep negations as findings with polarity=ABSENT. Unknown stays UNKNOWN and is never turned into ABSENT. Every finding has a source_span (start and end offsets into the original text; code verifies text[start:end] exists, else the finding is rejected) and origin=STATED or INFERRED (inferred items carry an uncertainty note). Terminology mapping uses a local file backend/app/agents/data/symptom_vocab.json (surface_form, normalized_term, vocabulary=LOCAL) built from terms in the fixtures plus a small documented common-symptom list; never claim UMLS, SNOMED, or MeSH unless a licensed resource is integrated; unmapped terms keep normalized_term=null. Required fields: age, sex, chief complaint, symptom duration. Detect contradictions by rules where possible, otherwise by LLM review. At most 5 clarification questions, each blocking (only when a required field is missing or a contradiction is unresolved) or non_blocking, with a reason. Invalid LLM JSON: one repair retry, then FAILED(INVALID_LLM_OUTPUT).
4.2 Symptom RAG Analyzer (AGT-2). In: ClinicalCase. Out: RetrievedEvidenceSet. Builds 1 to 3 RetrievalQuery objects from the structured findings (assembled by code, optionally expanded by the LLM; the final text is always stored), embeds them, searches Qdrant with optional metadata filters, deduplicates by chunk ID and text hash, ranks, and returns up to RETRIEVAL_TOP_K. Optional reranking is off by default and keeps the original score and rank in the trace. Each result carries evidence_id, document_id, chunk_id, title, source type, publication date if present, source location, retrieval_score, rank, corpus_version, embedding_model, query_id; evidence_level is UNKNOWN unless the source states a study type. It returns insufficient=True with a reason when too few passages pass the minimum score, when Qdrant is unreachable (VECTOR_DB_UNAVAILABLE), or when the collection is empty (EMPTY_CORPUS). On refinement it accepts alternative_query_hints. Its only prose is a short retrieval_summary whose every sentence cites evidence IDs (checked in code).
4.3 Evidence-Based Scanner (AGT-3). In: ClinicalCase, RetrievedEvidenceSet, optional gap_hints. Out: ExternalEvidenceSet. Builds focused PubMed queries, calls ESearch then EFetch, parses XML into EvidenceDocument (PMID, DOI if present, title, authors, journal, date, abstract, retrieved_at, source=PUBMED), flags records without an abstract as abstract_missing and excludes them from claim support, dedupes by PMID or DOI against local evidence, and chunks abstracts with the ingestion chunker. Per-query status is OK | EMPTY | TIMEOUT | RATE_LIMITED | MALFORMED | UNAVAILABLE; an unreachable source is marked UNAVAILABLE and never replaced with simulated records. With EXTERNAL_MODE=offline it returns status=SKIPPED_OFFLINE, and the report states that external scanning did not run. It flags staleness only by the STALE_YEARS rule and never declares a publication authoritative.
4.4 Clinical Data Fusion (AGT-4). In: ClinicalCase, both evidence sets. Out: CandidateClinicalReport with sections case_summary, relevant_findings, evidence_supported_observations, potential_considerations, alternative_explanations, contradictory_or_limiting_evidence, missing_information, uncertainty_and_limitations, recommended_evidence_review_steps, references. Patient facts and evidence go into separate, labeled prompt blocks; evidence text is wrapped as untrusted data. Every factual statement is a CandidateClaim (claim_id, text, category, section, evidence_ids, non-empty unless derived_from_patient_input=true, in which case patient_fact_ids is non-empty). Code rejects any cited ID not present in the evidence sets and re-asks the LLM once; a second violation drops the claim and records a warning. No treatment instructions, dosing, or forced single diagnosis; a regex lint in safety/forbidden_phrases.py fails reports containing imperative treatment or dosing language.
4.5 Adaptive Optimizer (AGT-5). In: report, verification results, evidence sets, iteration history, gate findings. Out: OptimizationIteration. selected_operation is one of REFINE_RETRIEVAL, FETCH_EXTERNAL, REVISE_REPORT, REQUEST_CLARIFICATION, STOP, chosen by rules (for example NO_RELEVANT_EVIDENCE leads to REFINE_RETRIEVAL; a DEGRADED scanner leads to one FETCH_EXTERNAL; unsupported or partial claims with some evidence lead to REVISE_REPORT; blocking missing patient information leads to REQUEST_CLARIFICATION). The LLM writes only the instruction text and query hints; it never picks the route or relaxes a criterion. Each iteration records iteration_id, index, trigger_findings, selected_operation, instructions, a machine-checkable completion_condition, result_status (CONDITION_MET | CONDITION_NOT_MET | NO_PROGRESS | BUDGET_EXHAUSTED), and report versions before and after. Stop with NO_PROGRESS when two consecutive iterations leave the set of non-SUPPORTED material claims unchanged. Report versions are immutable.
5. Approved extensions
5.1 Claim Verification Agent (EXT-A), claim_verification_agent.py, separate from Fusion. In: report and the union of evidence sets. Out: list[ClaimVerification]. Step 1, deterministic: every cited ID exists in this run's evidence sets, else UNVERIFIABLE with limitation CITATION_NOT_FOUND; patient-derived claims are checked against the case's source_spans. Step 2, deterministic where possible: numbers, units, and entity names in the claim must appear in the cited passage text; a claim with a number absent from every cited passage cannot be SUPPORTED. Step 3, model-based: an entailment-style judgment per (claim, cited passages) pair with a fixed rubric, returning a status and a justification that points to an evidence span by offsets; code verifies the offsets, and a judgment without a valid span cannot be SUPPORTED or CONTRADICTED. Statuses: SUPPORTED, PARTIALLY_SUPPORTED, CONTRADICTED, INSUFFICIENT_EVIDENCE, UNVERIFIABLE. It also scans the other retrieved passages for opposing statements and lists them as contradicting evidence. It may use its own model (VERIFIER_MODEL), never retrieves new evidence, and never edits the report.
5.2 Explicit Abstention (EXT-B), safety/abstention.py. AbstentionDecision: abstained, reason_codes (NO_RELEVANT_EVIDENCE, UNSUPPORTED_MATERIAL_CLAIMS, CRITICAL_SOURCE_UNAVAILABLE, UNRESOLVED_CONTRADICTION, INSUFFICIENT_PATIENT_INFO, OUT_OF_SCOPE, VERIFICATION_FAILED, ITERATION_BUDGET_EXHAUSTED, SYSTEM_ERROR, LOW_CONFIDENCE), explanation, affected_claim_ids, affected_sections, missing_evidence, missing_information, suggested_next_steps, requires (one or more of CLARIFICATION, RETRIEVAL, HUMAN_REVIEW). When abstained, the output contains only: the decision, verified-SUPPORTED observations (marked), the patient-fact summary, missing information, and next steps. No unverified considerations, speculative diagnoses, or filler.
5.3 Evidence-Level Provenance (EXT-C), provenance/. Relational edge tables link case, finding, query, evidence chunk, document, claim, verification, report section, iteration, abstention, and review event. Each edge has a relation (SUPPORTS | PARTIALLY_SUPPORTS | CONTRADICTS | INSUFFICIENT | DERIVED_FROM_PATIENT_INPUT | RETRIEVED_BY | GENERATED_IN) and a report_version_id. Provenance is written by the persistence step from real agent outputs, never reconstructed by an LLM. Claims and summaries are kind=INTERPRETATION; passages are kind=SOURCE; API and UI keep the distinction. assert_provenance_complete(report_version) fails if any material claim has no edge and runs at finalize and in tests. It records execution and evidence only, not model reasoning. Every state change, review action, and agent execution appends an immutable AuditEvent; the audit repository has no update or delete method, and a test asserts it.
5.4 Human-in-the-Loop (EXT-D). States: DRAFT, ANALYZING, EVIDENCE_REVIEW_REQUIRED, ABSTAINED, READY_FOR_REVIEW, REVIEWED, REVISION_REQUESTED, FAILED. Allowed transitions (all others raise InvalidTransition, HTTP 409): DRAFT to ANALYZING; ANALYZING to EVIDENCE_REVIEW_REQUIRED, ABSTAINED, READY_FOR_REVIEW, or FAILED; EVIDENCE_REVIEW_REQUIRED to ANALYZING; ABSTAINED to ANALYZING or REVIEWED; READY_FOR_REVIEW to REVIEWED or REVISION_REQUESTED; REVISION_REQUESTED to ANALYZING; REVIEWED to REVISION_REQUESTED; FAILED to ANALYZING. One pure table in orchestration/states.py; test every allowed and every disallowed pair. Review actions: REQUEST_CLARIFICATION, REQUEST_EVIDENCE_REFRESH, REQUEST_REVISION, MARK_REVIEWED, ADD_NOTE. MARK_REVIEWED is labeled "Reviewed by clinician", never "approved", "validated", or "correct". Notes are stored apart from AI content and labeled HUMAN. Reviews are append-only. Only clinician_reviewer and admin may act; viewer is read-only; authorization is enforced server-side on every endpoint. Each review records reviewer ID, time, action, report version ID, and outcome.

8. Safety and resilience
Urgency rule set. safety/urgent_rules.yaml holds explicit, human-readable patterns (for example chest pain with dyspnea, sudden focal neurological deficit, suicidal ideation statements, severe bleeding, anaphylaxis signs). Code matches them against the structured findings and raw text at submission, before and independent of analysis. A match shows the banner "Possible urgent presentation: do not delay appropriate urgent human assessment" immediately and writes an audit event. The file starts with a header saying it needs clinical review before any real use and is never described as clinically validated.
Prompt-injection defense. Retrieved text, PubMed abstracts, and user text enter prompts only inside delimited data blocks that state their content is data, never instructions. LLM output is never executed as code or a tool call; agents have no tools beyond injected dependencies; routing never reads LLM-generated control fields. A test feeds a [SYNTHETIC] passage containing injected instructions and asserts that routing and output schema are unchanged.
Privacy. No real patient data in tests. Secrets only from the environment; .env.example holds placeholders. Never log patient text.
Resilience. LLM and HTTP calls use at most 3 retries with exponential backoff and jitter. Every loop has a hard cap in code. Persist execution status before and after each node. Each of these failures maps to a defined state or error code and has a test: LLM unavailable, invalid LLM JSON, embedder unavailable, Qdrant unavailable, Postgres unavailable, NCBI timeout, empty retrieval, corrupt document, invalid dataset record, conflicting evidence, verifier failure, iteration exhaustion, invalid transition, unauthorized action, interrupted run.

9.3 Corpus facts and handling.
• Rows are annotator-selected snippets, not abstracts: section is abstract (64,275), title (7,610), or sections.0 (4,034); median length 173 characters, maximum 3,946; 1,621 rows are under 50 characters (including 1 to 5 character gene symbols); 261 texts are duplicated and 8 are shared by different questions; 48,949 distinct PubMed URLs.
• One row becomes one passage (chunk_index=0). Apply the chunker only to a row longer than the embedding model's token limit, continuing the chunk index. Keep short rows and flag them short_passage=true (under 50 characters); report the count.
• Platform evidence ID: ev:bioasq:<evidence_id>:<chunk_index>. The file's evidence_id is stored as legacy_id together with its file name; joining legacy IDs across two files without an explicit mapping raises an error. One EvidenceDocument per PMID (48,949); title, journal, authors, and date are UNKNOWN because the data does not contain them, and they are never fetched unless a separate, labeled enrichment run is added later.
• PMID extraction: apply (?:^|/)(\d{1,9})/?$ to pubmed_url. 245 URLs deviate from http://www.ncbi.nlm.nih.gov/pubmed/<digits>: https variants (116), bare digits (58), https://pubmed.ncbi.nlm.nih.gov/<digits>/ (45), trailing slash (15). Store the original URL and the PMID; reject and count rows with no match (expected 0).
• 24 snippets contain email addresses: author contact details in published text, classified AUTHOR_CONTACT. They do not block ingestion; the text stays verbatim and is never written to logs (counts only). Phone-like patterns: 0 found. Any patient-identifier pattern (names in clinical context, dates of birth, record numbers, phone numbers) stops work on that dataset: do not ingest, log only counts, and file a change proposal. Put the regexes in scripts/check_dataset_pii.py.
• Ingest corpus text only from this file, never from the context column. After ingestion, the Qdrant point count, PostgreSQL passage count, and source row count must be equal (75,919, fewer only for rows explicitly rejected and counted). corpus_version is the SHA-256 of the corpus file combined with the embedding model name and revision.
• Every retrieval result produced from this corpus carries the label CLOSED_WORLD_SNIPPET_CORPUS: each question's own answer-bearing snippets are inside the corpus, so retrieval is easier than real use and is not comparable to open-corpus or abstract-level results.
9.4 Questions file facts and parsing.
• Question types: factoid 1,695; yesno 1,541; summary 1,363; list 1,130. sample_id is unique. No duplicate question text after normalization. No split column. No PMID column.
• exact_answer, ideal_answer, context, source_reference, concepts, metadata are JSON text; all parse with json.loads (0 failures). Read every CSV with dtype=str, keep_default_na=False, encoding utf-8 then utf-8-sig (fail otherwise), keep multi-line quoted cells, never coerce identifiers to numbers, and read files over 200 MB in chunks.
• Accepted exact_answer shapes, nothing else (an unknown shape rejects the row and is counted): yesno is the JSON string "yes" (1,123) or "no" (418); factoid is a flat list of strings (1,695); list is a list of lists of strings (1,130; 1 to 42 entities, up to 12 synonyms each); summary is JSON null (1,363).
• ideal_answer is a JSON list of non-empty strings in all rows (1 string in 3,785 rows; up to 112 in one row; 54 rows exceed 20,000 characters).
• context is a list of snippet objects with keys beginSection, document, endSection, offsetInBeginSection, offsetInEndSection, text (80,058 snippets, median 9 per question, maximum 121); every snippet's document appears in the same row's source_reference. source_reference holds 61,506 PubMed URLs, all matching the PMID pattern. 22 context snippets contain emails (AUTHOR_CONTACT).
• concepts and metadata are validated to parse, then neither stored nor used.

• All 5,665 sample_ids in the corpus exist in the questions file. 64 questions (factoid 35, yesno 12, summary 11, list 6; 78 snippets) have no corpus rows: exclude them from retrieval metrics and count them.

9.7 Leakage rules. Only question and question_type may enter any query, prompt, or agent. exact_answer, ideal_answer, context, source_reference, concepts, metadata, source_dataset, and the corpus columns sample_id and question_type never reach the workflow, never appear in the Qdrant payload, and are never retrieval filters. Gold answers and the sample_id-to-passage labels live only in the PostgreSQL evaluation_labels table and are read only after retrieval, for scoring. PMIDs from source_reference are used only to compute the gold-document citation rate. section is ordinary passage metadata and may be stored as source_location. A leakage test searches every serialized agent input and query for gold answer strings, sample_id values, and snippet text.
9.8 Benchmark mode (evaluation harness only). BioASQ questions are not patient cases, so the harness runs the workflow with benchmark_mode=true, which changes exactly three things: (a) required case fields are empty, so no blocking clarification is raised for missing age, sex, or duration; (b) a biomedical factual question counts as in scope for gate rule 1; (c) output is labeled BENCHMARK, NOT CLINICAL USE. Gate rules 2 to 6, verification, abstention, and provenance are unchanged. The flag lives only in the harness, is applied identically in every ablation, and is recorded in the run file as [ENGINEERING-DECISION]. Default EXTERNAL_MODE=offline for benchmark runs so live PubMed search cannot reach gold documents outside the controlled corpus; an online run is a separate, labeled run.
9.9 Answer extraction and scoring. A separate AnswerExtractor step (own prompt and version) sees the question type, the question, and the generated verified report, never gold. Output: yesno gives yes, no, or ABSTAIN; factoid gives up to 5 ranked strings or ABSTAIN; list gives entity strings or ABSTAIN; summary gives short text drawn only from SUPPORTED or PARTIALLY_SUPPORTED claims, or ABSTAIN. If the workflow abstained, the extractor is not called; abstentions are never scored right or wrong, and every report shows both an answered-only and an all-questions view. Normalize before matching: lowercase, Unicode NFKC, strip punctuation, collapse whitespace. Scorers live in evaluation/bioasq_scoring.py, implemented from the published BioASQ evaluation guidelines with the version recorded; if the guidelines cannot be accessed, label the metric approximation and state its formula.
• yesno: accuracy and macro-F1.
• factoid: the gold list is treated as the acceptable surface forms of the one correct answer ([ENGINEERING-DECISION], needs human confirmation because the file does not say). Strict accuracy: rank 1 equals any gold string. Lenient: any of the top 5 equals any gold string. MRR: first rank equal to any gold string.
• list: per-question precision, recall, F1 against gold entities (a prediction matches an entity if it equals any of its synonyms), then the mean.
• summary: ROUGE-2 and ROUGE-SU4 against ideal_answer only if a pinned ROUGE implementation is installed, else "Not evaluated"; with several ideal answers, score against each and report the maximum.
• retrieval: Recall@5, Recall@10, Precision@5, MRR, MAP against the derived labels, with the number of questions beside each metric; after the platform deduplicates identical texts, a passage counts as relevant if any member of its duplicate group is relevant.
• grounding: gold_document_citation_rate = answered questions whose citations include at least one gold PMID / answered questions; reported separately from citation correctness.
9.10 Limitations to state in docs/evaluation_protocol.md. BioASQ training data is public, so a model may have seen these questions and answers and accuracy may partly reflect memorization. The corpus is closed-world: for 12 of the 30 smoke questions the opening of the first ideal answer appears verbatim in the question's own snippets. The data is a processed variant of unknown provenance. Results are benchmark measurements only and never evidence of clinical validity. ## Appendix A: Approved decisions (from Phase 0 review)

A1. Confidence formula (CP-04): approved as the documented alternative, tagged [PAPER-GAP] and [ENGINEERING-DECISION: CONF-FORMULA]. The paper names three qualitative factors (RAG similarity, external evidence score, concordance) and the threshold 0.65 [PAPER-VERIFIED: II-A.4, II-D]; the formula is not from the paper. In the baseline pipeline (no claim verifier), omit claim_support and use weights 0.40 retrieval_strength, 0.30 source_availability, 0.30 info_completeness [ENGINEERING-DECISION].
A2. Topology (CP-05): approved. Build the baseline first (SPEC nodes without claim_verification and evidence_safety_gate), then the extended graph. The node order stays sequential (scanner uses RAG gaps). Quote what the paper says about RAG and scanner running in parallel or in sequence, and record the difference as [ENGINEERING-DECISION].
A3. Iteration limit (CP-06): approved. In the full system, reaching the limit is never success: the gate decides (ready or abstain). When abstaining after the budget is spent, include ITERATION_BUDGET_EXHAUSTED plus the specific reason codes. The baseline follows the paper: it outputs the iteration-3 result labeled "BASELINE: budget reached, not verified".
A4. MedQA (CP-01), MedBullets (CP-02), PubMedQA (CP-03): deferred. Build nothing for them until a SPEC section is added.
A5. Candidate hypotheses (CP-07): the Symptom RAG Analyzer also outputs a list of CandidateHypothesis objects (label, supporting evidence_ids, retrieval scores). Code keeps a hypothesis only if at least one retrieved passage supports it, and rejects any cited ID not in the retrieved set. Hypotheses are "candidate considerations", never diagnoses. The Scanner builds one PubMed query per hypothesis plus queries for gaps. Fusion consumes the hypotheses. In benchmark mode, where the question is not diagnostic, the list may be empty and the Scanner uses gap queries. Add the CandidateHypothesis schema to the schema list.
A6. Embedding model: default is the paper's model BioBERT-mnli-snli-scinli-scitail-mednli-stsb [PAPER-VERIFIED: II-B.1]. Resolve its exact Hugging Face ID; if it cannot be found or loaded, stop and file a change proposal. NeuML/pubmedbert-base-embeddings is the fallback and never the silent default.
A7. LLMs: the paper uses different models per agent. This build uses one provider adapter with a separate model-name setting per agent (LLM_MODEL_CLARIFIER, LLM_MODEL_RAG, LLM_MODEL_SCANNER, LLM_MODEL_FUSION, LLM_MODEL_OPTIMIZER, VERIFIER_MODEL), all defaulting to LLM_MODEL.
